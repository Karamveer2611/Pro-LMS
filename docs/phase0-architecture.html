0 TL;DR

  • Modular monolith: Next.js + Laravel + PostgreSQL (managed, DO Bangalore) + Redis + S3-compatible storage + Bunny Stream. No payment gateway in V1.
  • Three roles only — Admin, Instructor, Learner — server-side Policies.
  • Commercial flow: catalog shows price as marketing info → Contact Admin → business happens off-platform → Admin manually enrolls. No checkout, no orders, anywhere.
  • Certificates are the largest V1 subsystem: Final Course Assessment–triggered, strict AND-only eligibility, per-batch overrides, dual-mode templates (designer + HTML), full revoke/replace lifecycle.
Timeline — fixed, not soft

Oct 20, 2026 is ~40 days out and is now the fixed target. Scope has been tiered P0/P1/P2 (§21) to fit — see §23 for the week-by-week plan and §24 for exactly where it's tightest.

5 Course & content model

Unchanged from Rev 2: Course → Module → Section → Lesson. Ordering, publish state, preview flags, completion tracking via one course_progress rollup service. No page-builder.

6 Enrollment & access-expiry model

The single most important domain rule — exactly one authoritative implementation: EnrollmentAccessService.

Course.default_access_days = 90 (nullable = lifetime) Batch.access_days_override = nullable (overrides course default for batch enrollments) On enrollment creation (V1: always created by Admin, source = 'manual'): enrolled_at = now() expires_at = enrolled_at + (batch.access_days_override ?? course.default_access_days) days (null if resolved value is null → lifetime access)
  • Access check — enrollment exists, status=active, not expired — called by every content-serving endpoint.
  • On expiry: learner keeps account, progress, any issued certificate. Content/video denied; "Access expired — contact admin to renew."
  • Admin extension is the only way to extend expires_at (audit-logged). Not a subscription engine.
Extensibility for future payments

enrollments.source has exactly one active value (manual) in V1. A future payments module would add a payment value and simply call the same enrollment-creation path Admin's manual flow already uses — no speculative order_id column or payment table exists today.

7 Drip content

Unchanged from Rev 2. Four release types (immediate, days_after_enrollment, fixed_date, days_after_batch_start), resolved by the same EnrollmentAccessService. The frontend never computes drip logic — it only renders the backend-resolved unlocked_at.

8 Batches, live sessions & attendance

Unchanged from Rev 2 — reconfirmed. Zero-or-more batches per course; batch_instructors vs. per-session instructor_id. No conferencing built. No automatic attendance detection of any kind. Batch-level access override and certificate override (§10).

Attendance — manual marking flow

  1. Admin schedules a session against a batch, assigns an instructor.
  2. Trainer opens the session, sees the batch roster.
  3. Marks present/absent/excused; "Mark All Present" is a frontend default, then exceptions are corrected.
  4. Submits as one bulk upsert — PUT /sessions/{session}/attendance, one transaction.
  5. Unique (session_id, user_id) — upsert updates, never duplicates.
Ownership & editing

Trainer marks/edits only their assigned session's batch roster. Self-correction window is a Settings value (default 7 days), Admin-only beyond that. Corrections write to the existing audit_logs table — never hard-deleted.

Reporting: session/batch/learner history, attendance %, counts. Learner sees only their own. Not a certificate condition in V1.

9 Assessments & Final Course Assessment

  • Question Bank — single source, tagged (subject/topic/exam/difficulty), reusable.
  • An assessment pulls a fixed question set (optionally shuffled per attempt, order-only).
  • Attaches to a module (module test) or a course (standalone) — never both. A standalone assessment can be explicitly designated the Final Course Assessment per course/batch (§10) — never assumed.
  • Attempts: nullable max-attempts/time-limit. Server-side scoring only. MCQ single/multiple-choice, true/false — no essay grading in V1.
  • Best valid attempt — highest-percent submitted attempt (ties by raw score); in_progress/expired never count. The 58%/74%/81% example uses 81%.

10 Certificate system

The largest V1 subsystem — four layers: Template → Configuration/Rules → Eligibility → Issuance.

10.1 · Configuration & the AND-only rule

CertificateConfigResolver::resolve(enrollment) 1. If enrollment.batch_id is set AND a certificate_configs row exists for that batch_id → use it. 2. Else use the certificate_configs row where batch_id IS NULL (the course default). 3. If neither exists, or is_enabled = false → not applicable; no evaluation runs.
#ConditionAlways required?Configurable?
0Final Course Assessment has ≥1 submitted attemptYes — trigger preconditionNo
1percent_complete >= cond_completion_min_percentOnly if enabledEnable + threshold
2best attempt percent >= cond_assessment_percent_minOnly if enabledEnable + threshold
3best attempt score >= cond_assessment_marks_minOnly if enabledEnable + threshold

eligible = conditions.filter(enabled).every(passed). No general-purpose rules engine — this fixed, structured set is the entire rule language.

10.2 · Auto-generation vs. manual

ON issues immediately via issueIfEligible(). OFF stops at eligible; Admin's "Generate" button calls the identical method.

statusLearner sees
not_applicableNo certificate UI
not_eligible"Certificate not yet eligible" (+ breakdown)
eligible"Certificate eligible" (+ "pending admin approval" if manual)
issued"Certificate issued — Download"

10.3 · Trigger flow & duplicate-generation prevention

sequenceDiagram
    participant Learner
    participant API as Assessment API
    participant Evt as AssessmentAttemptSubmitted (unique-by-attempt)
    participant Elig as CertificateEligibilityService
    participant Issue as CertificateIssuanceService
    participant DB as PostgreSQL

    Learner->>API: submit Final Course Assessment attempt
    API->>DB: attempts.status = submitted
    API->>Evt: dispatch(attempt_id)  [ShouldBeUnique]
    Evt->>Elig: evaluate(enrollment)
    Elig->>DB: bestValidAttempt(); upsert certificate_eligibility
    alt eligible AND auto_generate
        Elig->>Issue: issueIfEligible(enrollment)
        Issue->>DB: BEGIN; SELECT eligibility ... FOR UPDATE
        alt already issued
            Issue->>DB: ROLLBACK (no-op)
        else not yet issued
            Issue->>DB: INSERT certificates (unique: enrollment_id WHERE active)
            Issue->>DB: UPDATE eligibility SET status='issued'; COMMIT
        end
    end

Three independent layers prevent duplicates from a retried job, replayed event, double-clicked "Generate," or racing workers:

  1. Queue-level idempotency — unique job keyed by attempt_id.
  2. Row lock + short-circuit — SELECT...FOR UPDATE before checking status; both auto and manual paths share this one method, so a double-click hits the same lock.
  3. DB constraint backstop — partial unique certificates(enrollment_id) WHERE status='active'; a violation is treated as "already issued."

10.4 · Worked example

certificate_configs (course_id=12, batch_id=NULL) -- course default is_enabled=true, final_assessment_id=88, template_id=3, auto_generate=true completion>=80% assessment>=70% marks>=35/50 certificate_configs (course_id=12, batch_id=45) -- Batch A: no override → inherits default certificate_configs (course_id=12, batch_id=46) -- Batch B: explicit override is_enabled=true, final_assessment_id=88, template_id=7, auto_generate=false completion>=90% assessment>=80% marks>=40/50

10.5 · Template & designer architecture

Two authoring modes, one render pipeline:

  • Advanced (HTML/CSS) mode — edits template_html directly with placeholder tokens ({{learner_name}}, {{course_title}}, {{batch_name}}, {{completion_date}}, {{certificate_number}}, {{verification_url}}, {{qr_code}}) — used to recreate the ~19 existing Edmingle designs and by the team member comfortable with HTML.
  • Designer (drag-and-drop) mode — canvas for text, the same bindings, images (logo/signature/background), basic shapes. design_json is the editable element tree; every save compiles it deterministically into template_html — the exact same field HTML mode edits. Exactly one render path regardless of authoring mode.
  • Not a general page-builder — a fixed element palette, not arbitrary layouts or interactivity.
  • Canvas interactions: react-rnd (MIT, license verified directly from the repo) — thin usage, we own the element model and compiler.
  • PDF rendering: spatie/laravel-pdf, Browsershot (Chromium) driver — the default for certificates specifically (a change from Rev 2's DOMPDF-first stance), because designer-authored absolute positioning and web fonts need real CSS support. Accepted as a bounded ops cost (a small Chromium footprint) for visual fidelity.

10.6 · Revocation & replacement

Admin revokes → status=revoked, revoked_at/by/reason set. Never deleted; numbers/codes never reused by anything, revoked or not — no special reservation bookkeeping needed since the generator never looks at past allocations. Admin generates a replacement → new row, new number/code, replaces_certificate_id points at the original, goes through the same idempotent CertificateIssuanceService. The original being revoked means the partial unique index allows exactly one new active row with no special-casing. A revoked certificate's verification page still resolves and shows status: revoked — it never 404s.

10.7–10.9 · Verification, API, UI

/verify/{verification_code} — learner name, course, batch, number, issue date, status; no login, no other learner data.

API additions: GET/PUT .../certificate-config (course + batch), GET .../certificate-eligibility, POST .../certificates/generate, POST /certificates/{id}/revoke, POST /certificates/{id}/replace, GET .../assessments?standalone=true, template CRUD + compile endpoint.

UI: Course/Batch certificate-settings screens, a template list with a Designer/HTML mode switch (one-way "eject to code," not reversible), enrollment-detail condition breakdown + Generate/Revoke/Replace actions, learner status badge.

16 Database hosting recommendation

A definitive recommendation, evaluated against ~5,000 users, Indian user base, reliability, backups, cost, the Oct 20 deadline, and a small AI-assisted team.

OptionFit
DigitalOcean Managed PostgreSQL, Bangalore (BLR1)Entry ~$15/mo, automated daily backups + PITR included, no IOPS surprises, uniform pricing. App droplet in the same region keeps latency low for Indian users. Simplest ops for a small team — no VPC/IAM overhead. HA standby (+$30/mo) addable later.
AWS RDS PostgreSQL, Mumbai (ap-south-1)Enterprise-grade but real operational surface (VPC, IAM, Multi-AZ ≈2× instance cost) not justified at this scale/team-size unless there's existing AWS relationship.
Google Cloud SQL, MumbaiCompetitive at 8 vCPU+ tiers; not cheaper than DO at our small tier, similar overhead to RDS.
Self-hosted on the app VPSRejected — backup/PITR/patching/failover become manual team responsibility; not worth it given the Oct 20 timeline.
Recommendation

DigitalOcean Managed PostgreSQL, single node, BLR1 region, to start — add HA once usage/revenue justifies it. App server(s) in the same region.

19 Security checklist

  • Passwords hashed with bcrypt/argon2
  • Sanctum tokens, SameSite cookies, CSRF middleware
  • Every protected endpoint has an explicit Policy check, IDOR-suite verified
  • Server-side validation via Form Requests
  • Rate limiting on auth endpoints
  • File access via short-lived signed URLs only
  • Bunny Stream playback URLs signed, tied to authenticated + enrolled + drip-unlocked session
  • Secure HTTP headers (HSTS, X-Content-Type-Options, CSP)
  • Audit log: role changes, manual enrollment, expiry override, certificate revoke/replace, attendance correction, settings change
  • DB constraints back up app checks (certificate numbers, enrollment/attendance uniqueness, NOT NULL)
  • Certificate issuance in a locked transaction (§10.3) — the one place idempotency really matters without a payment webhook
  • Dependency scanning in CI
  • Secrets in environment variables, never committed
